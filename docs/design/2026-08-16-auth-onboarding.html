RouteReady · design · 16 Aug 2026

Five cards, then an account.

Sign-in is re-dressed onto the grouped-inset language Home now uses. Sign-up becomes a short interview: four questions that each change something a learner will see on their first screen, and credentials last.

Both phones below are running prototypes, not pictures. Sign in with a wrong password and watch it fail. Type into the password field on card 05 and watch the strength meter fill. Every duration is the real constant from src/ui/motion.ts — there is a slow-motion toggle if you want to see the choreography rather than feel it.

The shape

Questions first, account last

Supabase has email confirmation on, so signUp() returns no session — there is no signed-in user to write a profile to until the learner opens their inbox and comes back. Anything asked "after the account" would have to survive that round trip in local storage. Asking first avoids the problem outright: one call carries the answers with it.

02Test dateBooked, or not yet

The numbering is real: this is a sequence, each card is gated on the one before it, and the progress bar counts fifths.

Forgot password is new. resetPasswordForEmail was never wired, which means today an account with a mistyped password is simply lost. A sign-in screen without it isn't finished.

Watch the busy state, then the failure. The two links under the button both lead somewhere — try them.

Failure is quiet, and the app's motion rule survives intact. A shake was the obvious alternative and it is out: motion.ts says "nothing overshoots, so nothing settles, so nothing jiggles", and a shake is pure oscillation. Making one exception to a one-rule motion language is how a one-rule motion language stops being one. So the group's outline turns danger over 200ms and the reason slides down 6pt beneath it — no part of the screen moves back and forth.

What the shake was really for, the phone does better. A shake exists to make a failure register in the body rather than only in the eye. iOS has a dedicated channel for exactly that, and the app already uses it — Haptics.notificationAsync(Error), one asymmetric double tap that is unmistakably a "no". The failure is felt, and nothing on screen has to jiggle to say so. (The prototype can't fire it; a phone will.)

The sign-up interview

Tap the phone. Every transition below runs the real constants: 280ms entrances on Easing.out(Easing.cubic), 45ms between staggered children, 10pt of travel, and nothing that overshoots. Single-choice cards advance themselves once the selection has settled; the multi-select and the account card wait for the button.

Slow motion runs everything at a quarter speed so the choreography is legible.

Exactly one entry is off the decelerating curve, and it earns it. The spinner is linear and endless because it reports progress rather than arriving anywhere — a decelerating spinner reads as a stall. Everything else in the table is the same cubic, and nothing in the flow oscillates. The one animation that would have — a shake on a failed sign-in — was cut, and its job handed to the haptic channel instead.

Reduce Motion. Reanimated's builders default to ReduceMotion.System, so the entrances are already handled. The progress bar, the pulse and every strength animation are imperative withTiming calls and are not — they need an explicit useReducedMotion() check, or the one setting meant to calm the screen leaves the busiest thing on it moving. The meter still shows its state with the setting on; it simply arrives there without travelling.

Card 05

Password strength, and typing it twice

Type into the password field on the phone above — the meter is live. Four segments fill from the leading edge, 45ms apart, on the same decelerating cubic as everything else. The colour crossfades with the fill rather than snapping, so a password improving mid-word reads as one continuous move.

LevelReached bySegmentsRoleSays
EmptyNothing typed0label‑tertiaryAt least 8 characters
ShortUnder 80danger3 more characters
Weak8+, and nothing else1warningWeak — add a capital or a number
FairOne of the four2warningFair
GoodTwo of the four3accentGood
StrongThree or four4accentStrong

The four points are: twelve characters or more, mixed case, a digit, a symbol. No new colours enter the palette — danger, warning and accent are the app's existing three, used the way DriveModeRow already uses them.

Clearing eight characters is itself the first segment. The obvious alternative — score the four points and floor the bar at one segment — makes the first point invisible: the meter says "add a capital", you add one, and nothing moves. A meter that does not respond to the thing it just asked for is worse than no meter. So the bar shows 1 + points, capped at four. 

// src/lib/passwordStrength.ts — a function of the string, nothing else.
export type Strength = { level: Level; segments: 0|1|2|3|4; message: string };
export function passwordStrength(password: string): Strength;

Only the 8-character floor gates the button. Everything above it is advice. A meter that refuses to let you continue is a meter people defeat, and what they defeat it with is Password1! — which scores four segments and is on every breach list there is. The bar informs; it does not police.

The confirm field is back, and it is revealed rather than always there. It expands once the password clears 8 characters, on the same 280ms as the date row — before that there is nothing to confirm, and an empty second password box just makes the card look longer than it is. A tick fades in at the trailing edge when the two match. Mismatch says nothing until the field is left, because telling someone they are wrong halfway through typing a word is noise, not help.

Payoff

What each answer buys

A question that changes nothing is a toll. Each of the four earns its card:

AnswerKeyWhat it changes
Test centrehome_centre_idCentres opens on it instead of an unsorted national list. Its routes are the first thing in the app.
Test datetest_dateA countdown on Home, and it paces the "work on this next" card — six weeks out is a different suggestion from six days.
ExperienceexperienceWhether the first suggestion is a practice drive or a mock test.
Weak spotsfocus[]Routes carrying those hazards sort first, before any drive has been recorded.

The last three are the answer to the cold-start problem: Home's next-step card is computed from recorded drives, and a brand-new account has none. Today it has nothing to say. With these it does.

The weak-spots card offers four options, not six. hazards.type holds exactly roundabout, zebra, narrow and junction, and manoeuvres is a global reference table with no route link. So "parallel parking" would be a question the app has no way to act on. The card offers what the data can sort by and nothing else; adding parking means adding a route ↔ manoeuvre relation first, which is its own change.

Data

It rides in user_metadata

The same call sessionStore already made for the name, for the same reason: a table would need a row, a policy and a migration to hold four scalars that belong to the account. test_centres already grants select to anon, so the centre picker works before an account exists. 

// src/lib/onboarding.ts — pure, no React, no Supabase.
export type Answers = {
  centreId: string | null;
  testDate: string | null;          // ISO date, or null for "not booked"
  experience: "starting" | "progressing" | "ready" | null;
  focus: HazardKey[];               // 0–2
};

export const QUESTIONS: Question[] = [ /* the four, as data */ ];
export function canAdvance(step: number, a: Answers): boolean;
export function toMetadata(a: Answers, name: string): Record<string, unknown>;

// src/stores/sessionStore.ts — one changed signature.
signUp: (email, password, profile: SignUpProfile) => Promise<string | null>

The questions are data, not JSX. That is what makes the copy, the order and the gating testable without rendering anything, and it's why adding a fifth question later costs one array entry rather than one screen.

Scope

In, and deliberately out

In

Sign-in re-dressed. Forgot-password wired. The five-card flow with its motion. onboarding.ts and passwordStrength.ts with their tests. The animated meter and the revealed confirm field. signUp carrying the profile. The ten fixes above.

Out — separate work

Actually consuming the four answers on Home and Centres. The metadata gets written and tested here; the screens that read it are their own change, on their own screens.

Out — later

Sign in with Apple. Not required while email is the only method, and adding one third-party provider triggers App Store rule 4.8 — that's a decision, not a detail.

Two live phones, seventeen animations, one curve. Nothing on this screen jiggles.
