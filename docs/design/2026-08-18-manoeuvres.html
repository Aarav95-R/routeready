Manoeuvres

The fourth tab, and the last stub on the tab bar. Four manoeuvres, the copy for all of them already sitting in the database since Phase 1, and one thing the database cannot hold: where the car actually goes.

What was decided

Four answers that between them fix the whole shape of the work.

Purpose A reference, not a tracker Read-only. No ticking, no confidence rating, no “practised” state — so no new table, no RLS, no outbox.
Illustration Step-linked diagram One top-down scene per manoeuvre; the car moves and rotates to the pose for whichever step you are reading.
Detail layout Diagram pinned, steps scroll The diagram never leaves the screen. Scrolling the steps drives it, and so does tapping one.
Dependencies None added react-native-svg 15.12.1 and reanimated 4.1.1 are already installed and already used.

The two groups are the teaching

Three of these are reversing manoeuvres you perform off the flow of traffic; the fourth puts you on the wrong side of a live road. Grouping them says that before any copy does, and it costs one GroupHeader.

Thumbnails carry the difference

Bay park (reverse) and Forward bay park end in the same bay and read as the same row. The thumbnails differ in exactly one thing — which end of the car faces the aisle — because that is the entire difference between the manoeuvres. The lighter bar is the windscreen.

No empty state to design

The four rows are seeded reference data with a public read policy, cached on first fetch like listCentres. Offline after first launch, the screen is complete. A cold first launch with no network is the only empty case: skeleton rows, then the same “Try again” button Centres uses.

Two ways in, one state

The active step is one number. Tapping a row sets it; scrolling sets it to whichever row has reached the top of the list. Both write the same value, so the diagram never disagrees with what you are reading — the binding Centres already uses between its sheet and its map, applied to a much smaller list.

The car is the only thing that moves

Scene, path and dots are static. The car is a single Animated.View driven by one shared value per axis, on the Easing.out(Easing.cubic) curve already in src/ui/motion.ts. Reduced motion turns the transition off; the car still jumps to the right pose.

Why the diagram is pinned

Six steps and three tips overflow the screen on every manoeuvre. If the diagram scrolled with them it would be gone by step four, which is exactly where the steering instructions get hard to picture.

Worth a look on device

At 322pt wide the diagram card is about 290pt. The scene is drawn in a 320×190 viewBox, so kerb labels set at 11 units render near 10pt — legible, but the smallest type in the app. If it reads badly on a real phone, the labels go and the caption under the card carries them instead.

Where the geometry comes from

The one genuinely new idea in this screen, and the one thing that can break quietly.

  • A scene is one object. Static background elements, a poses array of { x, y, deg }, and nothing else. The pose array’s length must equal the manoeuvre’s step count — a unit test asserts that against the four seeded names, so a copy edit that adds a seventh step fails in CI rather than freezing the car on step six.
  • The fallback is silent and complete. An unrecognised name gets the steps and tips with no diagram card. Nothing is broken and nothing says “missing”, because a learner reading the steps has lost nothing they knew was there.
  • Names are the join key, so they are pinned. Parallel park, Bay park (reverse), Forward bay park, Pull up on the right — spelled in seed.sql and in manoeuvreScenes.ts, and the test above is what keeps the two spellings honest.

Every scene is drawn heading right, so deg 0 is nose-east and the kerb a learner parks against is the top edge. Pull up on the right is the one manoeuvre that finishes against the bottom edge, and that inversion is the diagram teaching the manoeuvre.

src/types/db.ts                    + Manoeuvre = { id, name, steps, tips }
  • No schema change. The manoeuvres table and its public read policy already exist and are already seeded.
  • Tests follow the house pattern: everything with a rule in it lives in src/lib and is tested there — grouping, blurbs, the pose-count invariant. The screens fetch and compose and decide nothing.
  • One line of SETUP.md changes: the sentence listing Manoeuvres among the Phase 2 stubs.

Deliberately not in this

  • No saved progress. No ticking steps, no confidence rating, no “practised” marks — so no user_manoeuvres table and nothing new for the Home screen to read.
  • No in-car checklist mode. The big-tap-target, haptic-per-tick mode from the Phase 1 spec is a different screen with a different posture, and it only makes sense once there is something to save.
  • No link from a route or a result. Tying a fault on a mock test to the manoeuvre that would fix it is a good idea and a separate one; it needs fault categories the scoring engine does not currently emit.
  • No video, no photography. A vector scene is the only illustration that stays sharp, ships in the bundle, and can be corrected in a diff.
