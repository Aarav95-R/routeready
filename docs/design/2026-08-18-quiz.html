Design · 18 August 2026 · Phase 2

Show Me, Tell Me

The last stub on the tab bar. Twenty vehicle safety questions the examiner can ask before and during your test — the copy for most of them has been sitting in the database since Phase 1, unread, behind a screen that says “Coming in Phase 2”.

What was decided

Four answers that between them fix the whole shape of the work.

Scope Show me / tell me only No Highway Code bank. That would be a second table and dozens of questions I would be inventing rather than quoting.
Answering Multiple choice, four options Pick one of four. The full model answer then appears as the thing to actually say aloud.
Memory On the device AsyncStorage, alongside the existing cache. No migration, no RLS, works with no signal.
Shape Browse, plus a round of ten The tab is a readable reference. A button on top of it deals ten questions one at a time and ends on a summary.

The tab

Every one of these questions opens with the same six words. Left as written, the list is twenty rows all beginning “Tell me how you’d check…”, and nothing is scannable. So the row leads with the subject and puts the phrasing underneath.

The row

Subject on top, phrasing underneath — the same two-line shape the manoeuvre rows already use, so the two reference tabs read as siblings. The phrasing line is not decoration: “show me” means you will be doing it while driving, “tell me” means you will be talking at the kerb.

Three states, one of which draws nothing

A green tick means you got it right last time. A clay dot means you did not. A question you have never seen shows an empty space, because twenty hollow rings would shout louder than the few ticks that carry the information.

Why the progress bar is clay and the button is green

theme.ts already splits these: green is the road — go, route, correct — and clay is you. “9 of 20 known” is a fact about the person, so it is clay. “Start a round” is an action, so it is green.

Tapping a row

Expands it in place to show the question in full and the model answer beneath — no navigation. Twenty detail screens for one paragraph each would be a push transition where a disclosure will do. One row is open at a time.

Two taps, not one

Picking an option only selects it. “Check answer” commits. On a 15 px list of four long options a mis-tap is easy, and a mis-tap that instantly and permanently marks a question wrong is the kind of thing people close an app over.

Red only at the moment of answering

A wrong pick gets danger and an error haptic, because that is genuinely an error and the feedback should land. By the summary it has cooled to clay — three red bars on a results screen reads as a telling-off, and this is the screen you see after every single round.

The model answer is the point

The multiple choice is a drill; the examiner will not offer you four options. So every answered question — right or wrong — reveals the DVSA answer verbatim, in quotes, as a sentence to say out loud. It is the last thing on screen before “Next”.

What the round deals

Questions you have never seen first, then ones you last got wrong, then the rest — shuffled within each band, ten in total. Option order is shuffled too, seeded per question per round, so the right answer is not always in the same place and a re-render never moves it.

Leaving early

The close button ends the round there. Everything already answered is already saved — results are written per question, not at the end.

Where the four options come from

The DVSA publishes questions and answers. It does not publish wrong answers, because the real test is verbal.

This is authored content, not sourced content

Three plausible wrong options per question, twenty questions — sixty sentences that I wrote. They are built by bending one real detail out of true: a threshold (1 mm instead of 1.6), a condition (warm tyres instead of cold), a symbol (three sloping lines instead of three horizontal ones). That makes them teach the detail that actually gets marked, but it also means a confidently-worded wrong answer is my sentence, not the DVSA’s. They live in scripts/seed/questions.ts and are worth a read-through before release. Two automated guards stand behind them: the right answer may never exceed every wrong one by more than ten characters, and it is never always the one written first — both are ways an option set becomes answerable without being read.

The options are short — ten to twenty words. The verbatim DVSA answers run to forty or fifty, and four of those stacked on a phone is a wall of text nobody reads. The long answer keeps its job: it is what appears after you commit.

What the data needs

Two columns and a reseed. show_me_tell_me already holds the question, the answer, the category and the is_show_me flag.

/** One option under a question. Exactly one per question is correct. */
export type QuizChoice = { text: string; correct: boolean };

export type QuizQuestion = {
  id: string;
  category: "safety" | "inside_car" | "under_bonnet";
  topic: string;        // "Tyre tread and condition" — the row's first line
  question: string;     // the DVSA wording, in full
  answer: string;       // the DVSA model answer, said aloud
  is_show_me: boolean;
  choices: QuizChoice[];
};
  • The bank gets rebalanced, as SETUP.md has been promising. It is currently 12 “inside the car”, 5 “safety” and a single “under the bonnet” row that crams oil, coolant and brake fluid into one question. That row becomes the three real DVSA questions it was standing in for, and the indicator and brake-light checks move to “safety and the outside”, which is where you actually do them — you get out and walk round the car. 18 becomes 20, split 7 / 10 / 3.
  • topic is a column rather than something derived from the question text. Stripping “Tell me how you’d…” off the front and re-casing the rest works for about fourteen of them and produces “Know if there was a problem with your anti-lock braking system” for the rest.
  • Results live in AsyncStorage under cache:progress:quiz — deliberately inside the prefix clearUserCache() already sweeps on sign-out, so the next person to hold the phone does not inherit the last one’s score. That function needed no change; a test asserts the sweep rather than the key string.

What gets built

The same split the manoeuvres work used: rules in lib, fetching in services, composition in the screen.

app/quiz/round.tsxThe round, and the summary at the end of it.

The summary is a state of the round screen, not a route of its own. A separate route would mean carrying ten answers across a navigation, which is a store — and the round is the only thing that ever reads them.

Not in this

  • A Highway Code bank. Ruled out above — a second table and content I would be authoring wholesale rather than quoting.
  • A two-question test simulation — one tell me at the kerb, one show me on the move, exactly as the real thing runs. Tempting, and cheap once the round exists, but it is a second mode competing with the one this screen is for.
  • Spaced repetition. “Known” means your last answer was right. A learner can explain that rule to themselves; a decay curve they cannot see is a screen that seems to forget things at random.
  • Quiz results on the Home dashboard. Needs the Supabase table this design deliberately does without.
